# DiskScope: code audit (read-only), 2026-11-16

Audited revision: detached HEAD on `9ea172e` (a local security branch, not yet merged at the time). No commit, push or deletion was made during the audit.

## Summary (10 lines)

1. **Repository state:** `origin` contained only `main` (9c4ab12, 2026-10-21, parts 1 and 2). The local security branch had 3 more commits, not pushed. No more recent work was visible on the remote: if it existed, it had not been pushed.
2. **Health:** the build passes with 0 warnings (TreatWarningsAsErrors) and the tests pass 217/217 in 5 s. The code is generally clean and documented. This is not a codebase to rewrite: it needs consolidation.
3. **Architecture:** 14 well-separated projects: Core, collectors, History/Diagnostics, Storage/Scanner, App. The App layer is the weak point: `MonitoringViewModel` (474 lines) acts as the composition root, refreshes the UI, builds reports and handles exports.
4. **Main UX bug:** there is no global exception handler. Async commands are `async void` via `RelayCommand`. A locked `Clipboard.SetText` or a non-IO export error crashes the app.
5. **"Unknown is not zero" rule bugs:** `default(MetricValue)` counts as "available". The per-core CPU bar shows 0. Folder sizes under access denied appear as exact (treemap tooltip, columns). Reports show "NaN %".
6. **Robustness bugs:** a subscriber that throws an exception kills a collector loop permanently (`MonitoringScheduler`). The Processes loop dies silently on any non-Win32 exception. The start-up inventory loses tasks on access denied, and task paths that are already quoted yield an unknown executable.
7. **Duplicates:** two CSV writers (`Storage/CsvExporter` and `Reports/CsvTable`): the formula neutralization from commit c1fc187 only covers the second. There are also three CPU delta calculations, two identical top-N heaps, four P/Invoke classes and two `AskSave*Path` methods.
8. **Traces of several LLMs:** explicit vs implicit usings, `OnPropertyChanged` vs `RaisePropertyChanged`, several types per file in half of the VMs, hard-coded colors in each view, tab literals `"5"` in XAML, isolated `s_` naming conventions.
9. **Dead code:** limited, about fifteen members. The App → Scanner.Ntfs reference is not used. The NTFS engine only exists as a benchmark probe, which is normal (blocked by elevation).
10. **Plan:** 7 batches. Batch 1 (safety nets, risk-free quick wins) and batch 2 (unknown is not zero) first. The large App refactor (batch 5) comes only after additional VM tests.

Reliability legend: **[V]** verified by the auditor in the code, **[R]** reported by a sub-agent and partially or not at all cross-checked. [R] items must be reconfirmed before fixing.

## 1. Current architecture

```
Core (metric contracts, alerts, findings, MetricFormatter)
 ├─ Monitoring (scheduler, clock, PdhQuery, DiskActivity, VolumeSpace)   net10.0 (!)
 │    └─ Monitoring.Gpu (DXGI + PDH GPU)                                   net10.0-windows
 ├─ Monitoring.CpuRam, Processes (+ SelfCollector), History, Diagnostics, Maintenance, Reports
Storage (NodeIndex SoA, builder, queries, search, treemap, CsvExporter)
 └─ Scanner (contracts, orchestrator, PartialResultSchedule)
      ├─ Scanner.Standard (GetFileInformationByHandleEx)
      └─ Scanner.Ntfs (USN parser, tree builder; prototype, only used by Benchmarks)
App (WPF, home-made MVVM) → references the 13 projects, including Scanner.Ntfs (unused)
Benchmarks (CLI); Tests (a single xUnit project that references everything, App included)
```

Strengths: invariants documented and respected (parent < child, logical/allocated never mixed, NodeStatus propagated); collectors without WPF; nullable MetricValue; tests on calculations.

Weaknesses:
- **App**: composition root in `MainWindow` (field initializer `ShellViewModel.CreateDefault()`) and in `MonitoringViewModel.CreateDefault()`. There is no global exception handler (`App.xaml.cs`, 5 lines). Business logic lives in the VMs: `ProcessesViewModel.Read()` detects memory growth and builds the tree, `MonitoringViewModel.BuildReport()` assembles the report.
- **Monitoring** targets `net10.0` but contains Windows-only PDH. Gpu references it only for `PdhQuery`.
- **Metric IDs** hard-coded in Diagnostics (`DefaultRules`, `CoincidenceRule`) even though constants exist in the collectors.

## 2. Target architecture (evolution, not a rewrite)

- **Core**: add `MetricIds` (all keys `cpu.total`, `mem.*`, `disk.*`…); `MetricQuality.Unavailable = 0`.
- **Monitoring.Windows** (or move Monitoring to net10.0-windows): `PdhQuery`, a single `NativeMethods` per native project, a single CPU delta (`CpuDelta`) reused by CpuCollector, ProcessCpuTracker and SelfCollector.
- **CSV**: a single `CsvWriter` (escaping + formula neutralization) used by `Storage.CsvExporter` and `Reports`.
- **App**:
  - `App.xaml.cs` = composition root + `DispatcherUnhandledException` / `TaskScheduler.UnobservedTaskException`.
  - `AsyncRelayCommand` that captures and reports exceptions.
  - Services `ExportService` (temp write + rename, broad try/catch), `ProcessMonitor` (loop + Read outside the VM), `ReportBuilder`.
  - One type per file; shared `ResourceDictionary` (colors, DataGrid styles, cards).
  - Tab constants via `x:Static`.
- **Tests**: separate pure tests from WPF tests; mark tests that read the real registry or SCM with `[Trait("Category","Machine")]`.

## 6. Inconsistencies left by several authors

- **Usings:** explicit (`System`, `System.Collections.Generic`) in `NodeIndexQueries`, `ExtensionStats`, `NodeSearch`, `TreemapLayout`, `CsvExporter`, `ObservableObject`; implicit elsewhere. Not sorted (`MonitoringViewModel.cs:1-17`).
- **Types per file:** one only in Storage, but three in `ProcessesViewModel.cs`, three in `MetricTileViewModel.cs`, several in `AlertViewModels.cs`.
- **Constructors:** classic (`RelayCommand`) and primary (`ParameterCommand`) mixed. Notification via `OnPropertyChanged` or via `RaisePropertyChanged`.
- **Errors:** collectors return `CollectorError`, `ProcessReader.ReadAll` throws `Win32Exception`, `SelfCollector` reports nothing. Exception filters differ across methods (`ReadKey`, `ReadFolder`, `ReadTasks`).
- **Metric quality:** `DiskActivityCollector` marks everything `Derived`, CpuRam marks raw values `Measured`.
- **Naming:** a single `s_` (`ProcessReader.cs:20`). `Native.cs`/`Dxgi` vs `NativeMethods`.
- **XAML:** `CommandParameter="5"`/`"3"` instead of `ShellViewModel.HistoryTab`/`ProcessesTab`. `Binding Path=Path` vs short form.
- **Tests:** namespace `DiskScope.Tests` for `Storage/CsvExporterTests`, whereas the others use `DiskScope.Tests.<Area>`. The CSV tests are in `InventoryTests.cs:37-69`, and `ProcessCsv` is in `ReportTests.cs`.

## 7. Test gaps

- **No tests:** `StartupInventory` (except `CommandLine`), start-type mapping of `ServiceInventory`, `CsvTable.IsFormulaLike` (edge cases), `HtmlReportWriter` (empty series, Samples=0), Benchmarks, `ShellViewModel`, `StartupViewModel`, `SparklineControl` (NaN, default End). [R]
- **Machine-dependent:** `InventoryTests.cs:81-90` requires zero errors and the EventLog service in Running/Auto, so it fails on a locked-down machine. `:93-99` asserts nothing useful. `ReportTests.cs:61` is fragile if the user name is short. [R]

## 9. Limits of this audit

- Storage, Scanner, Scanner.Standard, `UsnTreeBuilder` and the main ViewModels were read in full. Monitoring, Processes, Maintenance, Reports, NTFS and XAML were reviewed by three sub-agents ([R]), with occasional cross-checks (CommandLine, AlertEngine, MonitoringScheduler).
- The app was not launched and nothing was measured: B16/B17 remain performance hypotheses.
- Build and 217 tests were run in a separate worktree. The bin/obj folders were generated there, with no effect on the main repository.
